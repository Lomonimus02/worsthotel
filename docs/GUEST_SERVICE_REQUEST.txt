You are continuing development of the EXISTING Unity project:

THE WORST HOTEL EVER

Do NOT create a new project.
Do NOT rebuild existing working systems.

The current version already includes the work from Prototype 0.3 — Guest Agency.

This next iteration is:

PROTOTYPE 0.3.1 — GUEST SERVICE LAYER

This is NOT a large new milestone.

The purpose is to complete the Guest Agency milestone by adding the missing middle layer between:

NORMAL GUEST LIFE

and

SERIOUS COMPLAINTS / INFRASTRUCTURE FAILURES.

The current game has improved guest behavior and better causal incidents.

However, playtesting revealed:

- guests now live more believable lives;
- infrastructure incidents such as boiler and electrical problems can be interesting;
- but normal hotel operation sometimes feels too passive;
- there is not enough sense of "servicing hotel guests";
- we must NOT solve this by generating many random fetch quests.

The target is:

SMALL, MEANINGFUL, SYSTEMIC HOTEL SERVICE.

==================================================
1. CORE MODEL
==================================================

Guest-related events should now exist at three levels:

LEVEL 1 — ACTIVITY

Guest simply lives.

Examples:

Sleep.
Shower.
Watch TV.
Leave hotel.
Work.
Rest.

No player action required.

No notification unless relevant.

------------------------------

LEVEL 2 — SERVICE NEED

Guest wants something from the hotel.

This is not yet a complaint.

Examples:

Extra blanket.
Late checkout.
Luggage storage.
Wake-up call.
Request that another guest reduce noise.

The player may:

help;
decline;
delay;
sometimes ignore.

These should create light hotel work.

------------------------------

LEVEL 3 — INCIDENT / COMPLAINT

Something is actually wrong.

Examples:

Room is extremely cold.
Persistent noise.
Power outage.
Boiler problem.
Concrete room fault.

These are more serious.

The goal is a natural day rhythm:

ACTIVITY
→ SERVICE
→ ACTIVITY
→ SMALL DECISION
→ INCIDENT
→ CONSEQUENCE

Not:

ACTIVITY
→ NOTHING
→ NOTHING
→ BOILER EXPLODES.

Service needs should originate from:

Do NOT generate meaningless requests purely to keep players busy.

==================================================
5. EXTRA BLANKET
==================================================

Add a physical:

EXTRA BLANKET

system.

This is one of the key service interactions.

A guest may request an extra blanket when:

they are mildly uncomfortable from cold

but

the situation has not yet become a serious temperature complaint.

Example thresholds conceptually:

Comfortable:
no request.

Mildly cold:
possible blanket request.

Very cold:
temperature complaint / escalation.

Exact values must be configurable.

==================================================
6. BLANKET EFFECT
==================================================

A blanket should NOT increase actual room temperature.

Instead it improves:

GuestPerceivedTemperatureComfort

or equivalent.

Example:

Room temperature:
18 C

Blanket comfort bonus:
guest experiences it as tolerable.

This creates an important distinction:

BLANKET

Pros:
- no electricity;
- cheap;
- fast;
- simple.

Cons:
- limited effect.

PORTABLE HEATER

Pros:
- stronger temperature solution.

Cons:
- consumes electricity;
- may contribute to circuit overload.

BOILER REPAIR

Pros:
- systemic solution.

Cons:
- potentially more work / money / risk.

ROOM MOVE

Pros:
- potentially solves issue completely.

Cons:
- consumes another room.

This is exactly the type of systemic choice the game needs.

Example:

No 10-second Hold E.

==================================================
9. LATE CHECKOUT
==================================================

Add:

LATE CHECKOUT REQUEST.

This is primarily a MANAGEMENT interaction.

Guest asks:

"Can I check out later?"

Player can:

ACCEPT

or

DECLINE.

If accepted:

- guest occupies room longer;
- checkout time changes;
- room turnover begins later;
- room may not be ready for an incoming guest.

Guest should preferably offer:

additional payment

or

satisfaction benefit.

This creates a real tradeoff.

==================================================

==================================================

This is meaningful.

==================================================
13. WAKE-UP CALL IMPLEMENTATION
==================================================

Use hotel simulation time.

At the requested time:

This should take only a few seconds.

Do not make it a minigame.

==================================================

==================================================

small dissatisfaction.

Do NOT make missing one wake-up call catastrophic.

This is a soft obligation.

==================================================

- traits influence probability;

54. ACCEPTANCE CRITERIA
==================================================

Prototype 0.3.1 is complete when:

1. Normal guest life continues to exist without constant player intervention.

2. Service Needs exist between normal activity and serious complaint.

3. Service needs are causal, not random chore spam.

4. Same service need does not create repeated notifications.

5. Extra blanket physically exists.

6. Blankets come from linen storage.

7. Blanket improves guest comfort without heating room.

8. Portable heater remains a stronger but electrically expensive alternative.

9. Room radiator can be adjusted physically.

10. Radiator setting affects boiler demand.

11. Late checkout is a genuine management decision.

12. Late checkout affects room availability / turnover.

13. Wake-up calls work within one-night stays.

14. Wake-up calls create a delayed promise.

15. Forgetting a promise has a modest consequence.

16. Luggage storage exists.

17. Noise service requests still require real noise sources.

18. At least 1 concrete room fault exists physically.

19. Electrical reset does not magically solve overload.

20. Infrastructure failures are not artificially forced.

21. A day with no boiler failure can still feel occupied.

22. Player can proactively prepare for upcoming work.

23. Solo remains fully testable.

24. LAN co-op continues working.

25. No multi-day stay system was added.

==================================================
55. NORTH STAR
==================================================

The player should feel:

"I am operating a hotel."

Not:

"I am completing hotel-themed quests."

A good service interaction is:

A guest has a reason to need something.

The player understands why.

The player decides whether it is worth responding.

The response uses the physical hotel.

The response changes simulation state.

Sometimes the response creates a new tradeoff.

Example:

Guest is slightly cold.

↓

Requests blanket.

↓

Player has only one blanket left.

↓

Player gives it.

↓

Later another guest becomes cold.

↓

Now player must choose:
heater,
radiator,
room move,
or leave them uncomfortable.

That is hotel gameplay.

Protect this principle.
