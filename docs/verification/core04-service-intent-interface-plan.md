# Prototype 0.4 — интерфейс и сеть для Service Intent (план Phase 4)

27 сентября 2026. Документ подготовлен во время проверки Phase 3. Это предложение контракта, не реализованные API и не результат запуска. Runtime-файлы в рамках этого аудита не менялись.

Основание: точные разделы 42–49, 72–74, 82 и 92 [CORE04_REQUEST.txt](../CORE04_REQUEST.txt). Пользователь требует три отношения услуги к поведению гостя: **Remote**, **DropOff**, **Direct**. Их нельзя свести к одному «заданию» или к локальному флагу открытого меню. Известность проблемы персоналу остаётся отдельной характеристикой.

## Что должен видеть игрок

| Отношение | После реального сообщения гостя | Поведение и завершение |
| --- | --- | --- |
| Remote | «В комнате холодно» / «Ждёт улучшения условий». Местонахождение гостя — только обычный видимый статус, без назначения маршрута решения. | Гость продолжает расписание. Ремонт меняет фактическую комнату; отсутствие гостя не означает успешное решение. После возвращения и обновления восприятия действует обычное устойчивое восстановление. |
| DropOff | «Оставьте одеяло у двери комнаты 101» либо у другой конкретной разрешённой точки. После доставки: «Оставлено; гость ещё не получил». | Настоящий предмет должен прибыть в указанную точку. Получение/подтверждение при возвращении отделено от доставки. Игроку не требуется догонять NPC или получать доступ к спящему гостю. |
| Direct | «Ждёт разговора на ресепшене» / «Ждёт обмена ключами в комнате», при необходимости — понятное время окончания ожидания. | Авторитетное ожидание запрещает новый сон, душ или уход, но имеет конечный срок. Закрытие интерфейса не завершает намерение. Решение, отказ, реальная передача ключа или истечение срока завершают его по правилам модели. |

До коммуникации сохраняются существующие `ServiceCase.IsKnownToHotel` / `HotelIncident.HasContactedStaff`: никакой подробной карточки намерения, причины, точки доставки или инструкции. Общий звонок и физически ожидающий человек остаются допустимыми сигналами. F2 может показывать приватную диагностику отдельно от обычного интерфейса.

## Изменения существующих поверхностей

- `UI/GuestLabels.Communication.cs` и `GuestLabels.Services.cs`: единая формулировка отношения и состояния. Технические `Remote/DropOff/Direct` удобны в F2; обычному игроку нужны конкретные фразы выше.
- `UI/ManagementUI.ServiceBoard.cs`: одна известная карточка на прежний case/response; текст «ожидает ответа», «ждёт передачи», «доставлено, ждёт получения». Доставка не равна `Fulfilled`, если гость её ещё не получил. Время — через `GuestLabels.HotelMoment`, не отдельные локальные часы.
- `UI/ManagementUI.Context.cs` и `ManagementUI.GuestDetails.cs`: прямой разговор/обмен ключами доступен в авторитетном состоянии ожидания. При уходе, завершении или timeout список действий перестраивается по той же записи. Закрытие меню снимает только UI/физический grant. «Отменить переезд» действительно освобождает резерв комнаты и ожидание.
- `UI/ManagementUI.IncomingCalls.cs`: принятие звонка раскрывает сообщение, но само по себе не означает завершение Direct-решения; принятая просьба об одеяле объясняет точку DropOff. Исходящий wake-up остаётся отдельным обещанием с реальным телефоном.
- `UI/ShiftHUD.Services.cs` / `.Situations.cs`: низкая срочность просьб остаётся отдельно от серьёзных жалоб. Не создавать вторую карточку для Direct/DropOff поверх уже известной проблемы. После timeout текст меняется, не запускается бесконечный новый звонок.
- `UI/DeveloperPanel.GuestResponses.cs`: выбранный гость, тип/состояние intent, владелец ожидания, начало/deadline, точка доставки, ID/поколение предмета, время доставки/получения и причина завершения. Диагностический запуск по-прежнему создаёт причинные условия, а не готовый результат.
- Список гостей, детали и housekeeping пока собирают controller-actions в `OnGUI`, в отличие от новых Operations/context/service panels. При изменении этих поверхностей вынести коллекцию действий в Update и рисовать ту же коллекцию — это предотвращает сохранение предыдущих действий при переходе без repaint.

## Физический путь: что сейчас мешает

`Environment/RoomBlanketDeliveryInteraction.cs` сейчас требует `guest.Agent.InAssignedRoom`; `GuestServiceSystem.Items.DeliverBlanket` повторяет это условие и немедленно даёт `BlanketComfortBonus` / `Memory.BlanketsDelivered`. Поэтому отсутствующему гостю оставлять одеяло пока нельзя. Удалить только проверку присутствия недостаточно: получится мгновенная невидимая выдача.

Минимальный целевой путь:

1. Модель согласует существующий известный DropOff intent с конкретной точкой и гостем текущего проживания.
2. Физический `RoomBlanketDeliveryInteraction` либо новый соседний компонент показывает эту точку. Наружная полка/сервисная точка у двери позволяет доставку без нарушения приватности. Разрешённая внутренняя точка может остаться дополнительным вариантом.
3. `GameSession.GuestServices.DeliverBlanket` сохраняет текущую проверку настоящего сфокусированного collider, расстояния, held item, actor и владельца. Вместо одного `room.GuestId` передаёт модели идентичность intent/точки и ожидаемую версию.
4. Модель атомарно снимает владение предметом и фиксирует доставку этого item ID/Generation именно этому проживанию. Физический адаптер отпускает joint только после успеха. Повторная команда, чужое одеяло, неверная точка, отменённая просьба или переиспользованный номер отклоняются до изменения.
5. Видимый предмет остаётся в точке; он не исчезает из-за отсутствия NPC. При реальном возвращении/доступности модель подтверждает получение один раз, затем применяет личный комфорт/память и обычную проверку восстановления условий. Следующий жилец не наследует чужую доставку.

Существенная неоднозначность текущей модели: `ServiceKind.ExtraBlanket` в natural communication сейчас означает мягкую жалобу на холод, а обычная фраза принятия — «I'll look into the temperature». Поэтому нельзя автоматически превратить каждый такой case в обязательную доставку. По заданию холод — Remote, просьба оставить конкретное одеяло — DropOff. Возможный минимальный переход: исходная жалоба остаётся Remote, а явное соглашение «I'll leave a blanket at…» добавляет ожидаемую доставку к той же истории проблемы. Доставка при сильном холоде не обязана немедленно закрывать исходную температурную жалобу. Точную модель перехода согласовать до реализации, без дублирующих карточек.

Для Direct существующий `GuestServiceSystem.Communication.Communicate` вызывает `ClearGuestResponseAction` сразу после раскрытия сообщения; этого недостаточно для последующего решения. `HotelSimulation.Relocation` уже резервирует destination в `PendingMoveRoomId`, но валидация требует `InAssignedRoom`. Нужно согласовать с единственным intent ожидание в комнате либо у стойки и реальные правила ключей. Нельзя включать второй независимый FSM в UI.

## Предлагаемый минимальный контракт (имена ещё не согласованы)

Одна авторитетная запись `ServiceIntent` с `Id`, `GuestId`, типом/состоянием, ссылками на существующие case/response или конкретное действие переезда, `Version`, `StartedAt`, `Deadline`, местом ожидания и причиной завершения. Для DropOff — `DeliveryPointId`, `DeliveredItemId`, `DeliveredItemGeneration`, `DeliveredAt`, `ReceivedAt`. Для гостя — ссылка на единственное активное Direct-ожидание; remote issue / delivery expected должны вычисляться из тех же записей.

Это не новый генератор просьб. Существующий Response продолжает отвечать за наблюдение, самопомощь, контакт и раскрытие информации; intent определяет, что требуется после согласования. У одного гостя могут продолжаться Remote-условия, но одновременно владеть его расписанием должно только одно прямое ожидание. Phone/reception/room — канал контакта, а не тип услуги.

Обычная просьба не создаётся в несовместимом окне расписания (§48): сон/душ, imminent checkout/LeaveHotel или другая обязательная активность откладывают оценку. Это проверка модели при генерации/переходе, не только скрытая кнопка UI.

## Wire и команды

- Host передаёт intent и связь с агентом в обычном model snapshot. Replica только отображает deadline, не отсчитывает собственный timeout и не применяет comfort при чтении карточки.
- Валидация до любого restore: enums, конечные абсолютные времена, уникальные ID, существующий guest/case/response, допустимая точка/комната, действительное поколение item; связь waiting-state ↔ активный Direct; Delivered/Received не противоречат предмету и проживанию.
- Прямые решения через существующие `RespondService`, `MoveGuest`, `CancelMove`, `OfferCredit` должны привязываться к текущему intent ID/version, чтобы старое меню не отвечало на новое ожидание. Конкретное расширение envelope согласовать с root; не обходить grants для телефона/разговора и не доверять actor ID из payload.
- Физическая DropOff-доставка может остаться обычным world input, исполняемым host. Отдельный клиентский «выдать предмет» RPC не нужен. Новую статическую точку и её видимый предмет/подпись зарегистрировать в обычном world replication.
- Изменение snapshot-полей/поведенческого контракта требует согласованного wire/model version bump. Текущие версии Phase 3 — 7/6; финальный номер следующей версии фиксируется после контракта, mixed-build совместимость не обещается.
- Retention должен удерживать незавершённый intent, связанную доставку и проживание, даже если открытый UI закрылся или календарная дата сменилась. После завершения история освобождается без повторной оплаты/памяти/сигнала жалобы.

## Проверки следующей фазы

1. Direct ждёт через границу плановой активности: ни Sleep, ни Shower, ни LeaveHotel; закрытие меню не освобождает guest. Deadline освобождает его один раз и оставляет объяснимый результат. Отдельно завершение настоящим обменом ключей.
2. DropOff: известная просьба → фактический уход гостя → настоящие pickup/carry/delivery к разрешённой точке → отложенное получение при возвращении. Между доставкой и возвращением нет comfort/memory double-credit. Неверная точка/владелец/устаревшая версия не меняют предмет.
3. Remote: холод → гость Away → физическое улучшение отопления → возвращение → измеренное восстановление; уход сам по себе не закрывает проблему успешно.
4. UI с контроллером без зависимости от repaint: диалог Direct, закрытие/повторное открытие, истечение ожидания, отображение оставленной и полученной доставки. Приватный case не раскрывается преждевременно.
5. Snapshot/реальный LAN: те же intent IDs/версии, waiting и delivery state, timeout только на host, отказ stale action, атомарный отказ повреждённой связи. Смена даты не сбрасывает ни ожидание, ни доставку.

Проверки §72–74 и человеческий сценарий §82 остаются будущими gates. Этот документ их выполнение не подтверждает.
