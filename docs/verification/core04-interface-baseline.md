## UI and physical interaction assumptions

`ManagementUI.Open` requires `Session.Plan`, automatically chooses an application, and blocks both local staff when phase is not Service (`Scripts/UI/ManagementUI.cs:26–41`). `Update` automatically opens the first ledger; `OnGUI` chooses the complete layout by phase (`:55`, `:110`). Planning displays `DAY … OF 3`, `START SHIFT`, a locked plan, and forecast totals (`:142`, `:207`). Settlement/maintenance/results occupy the full screen and their buttons advance the world lifecycle (`ManagementUI.Service.cs:46`, `:82`; `ManagementUI.Maintenance.cs:21`, `:55`, `:63`).

For continuous operation, an operations/booking/report view must be an explicit local panel choice, not a simulation phase. Opening it may block that actor's movement, as current Service UI does, but must not stop the hotel or the other actor. Creating a report must not auto-open, close a phone or invalidate an ongoing physical interaction. The existing explicit session pause remains separate.

Current reusable presentation:

- `ManagementUI.ServiceBoard.cs:145` has compact NOW/UPCOMING columns and stable selection by case ID. It knows only existing guests' arrivals/checkouts and accepted wake promises; it cannot show tomorrow's unaccepted offers or reservations. Keep known-service cards separate from booking/calendar entries.
- `ManagementUI.ServiceBoard.cs:59` and `ManagementUI.Context.cs:32` rebuild selectable actions in Update, outside OnGUI. New operations/booking/report tabs should use the same pattern so keyboard/controller input works when rendering is delayed or absent. Old planning actions currently rely on OnGUI.
- `GuestLabels.Services.cs:35` formats an elapsed duration as `m:ss`; every current “hotel time” uses shift seconds. Split absolute calendar formatting (`Day 2 · 08:30`, or TODAY/TOMORROW plus time) from durations (`in 20 min`). A wake promise near midnight must not display a duration as a time of day.
- `ShiftHUD.cs:19–33` is Service-only and leads with a shift countdown. Replace with calendar time, occupancy, cash and readable capacity status. Avoid making midnight a deadline alarm.
- `ManagementUI.Electricity.cs:9` estimates only assigned-room baseline per circuit. `PlanningSystem.ProjectedLoad` is only the sum of archetype heating demand. Neither is a candidate comparison, condition-aware forecast or shower peak estimate.
- `ManagementUI.Service.cs:22` and settlement receipt rows assume the short single-shift guest list. Continuous history requires active/current filtering and paging; report history must not grow the guest ledger beyond its six-row layout.
- `RoomStatusPlaque.cs:58` changes its reservation source by Planning phase. It should instead distinguish occupied, preparing, ready and next reservation time without displaying a future booking as current occupancy.

Service visibility is already centralized in `GuestLabels.Communication.cs:9` (`ServiceCase.IsKnownToHotel`, incident `HasContactedStaff`). Preserve this gate for board/HUD/context/world text; a new intent or report must not reveal uncommunicated cause details. Generic ringing/waiting-person cues remain generic.

`GameSession.Conversations.cs:27`, `:67`, `GameSession.GuestServices.cs:81`, `:120` and `GameSession.GuestResponses.cs:13` explicitly require Service. The phone and incoming cue also gate on Service; radiators/breaker/linen accept Planning or Service; heater power permits Service. Audit these through one operating-state predicate rather than substituting report day for permission. Keep physical distance/source, actor/item ownership, room/guest identity, privacy and bounded conversation/phone grants. Their real-time grant deadlines are not calendar deadlines.

## WAIT, pause and real time

`WaitController.cs:71` blocks prepared Planning until CommitPlan, permits WAIT only during preparation/service, then checks pause/devices, UI, carried body, physical interaction and unacknowledged known critical situations. `:137` observes `EventRevision` after **every** hotel tick; a changed event stops the accelerated batch and requires button release before rearming. `GameSession.Service.cs:49–57` preserves this exact-tick stop. This behavior should survive the calendar refactor.

Recommended replacement: permit WAIT whenever the authoritative hotel is operating and the existing interaction/consent blockers allow it, including zero occupancy and quiet periods. Remove only the “commit plan first”/terminal phase assumption. Calendar report publication may be a single meaningful event if desired, but cannot permanently block WAIT or reopen the ledger. Booking/arrival/contact/failure/repair events need deliberate event semantics, not a new event on every demand or clock change.

`HotelGameClock.cs:12` is already a simulation-owned clock; speed 1/4/8 budgets fixed ticks and does not speed physics. `LocalCoopBootstrap.cs:254` separately sets Unity `timeScale` to 0/1 for pause. Offline focus loss pauses; LAN focus loss suppresses that machine's input, while a host menu pauses hotel state and propagates to the client. `GameSession.Service.cs:40` early-outs while paused. Preserve this role distinction and the diagnostics hooks. Do not add OS/wall-clock elapsed catch-up on resume or feed calendar days as one giant Tick.

`AdvanceToNextEvent` currently terminates through the service phase/end (`GameSession.Service.cs:151`). With an endless operating phase, the developer action needs an explicit bounded simulation horizon/maximum tick count and a “no event within horizon” result. Existing WAIT is frame driven and does not require an unbounded synchronous search. `AdvanceTime` currently clamps to one ServiceSeconds interval (`:138`); define a bounded diagnostic limit independently of a day length.

## LAN and read-only mirror migration

Baseline: `LanProtocol.Version=6`, compatibility `worst-hotel-0.3.2-natural-service6-gzip` (`Scripts/Networking/LanProtocol.cs:44`); model schema 5 (`Scripts/Simulation/HotelModelSnapshot.cs:8`). This wire schema is incompatible with scheduled reservations/calendar/capacity/intent state. A coordinated release bump (proposed protocol 7/model 6 plus a 0.4 compatibility string) is needed once the exact DTOs land; do not reuse old enum numeric values for a different command.

1. **Remove day as a transaction lock, preserve authority.** `LanProtocol.ValidCommand:54` currently demands exact `day` and `phase`. A legitimate phone, credit or booking command sent immediately before reporting boundary would be rejected after it. Preserve epoch, increasing command sequence, assigned actor, bounded payload and host availability; add operation-specific ID/revision/state checks for booking/maintenance. A broad “all world revision must match” would be just as brittle because ticks continue while the panel is open. Old version/epoch/replayed commands still fail.
2. **Model mirrors remain read-only.** `GameSession.Lan.cs:59` rebuilds the plan, applies the model and sets Report null in Service (`:69`); `:73` auto-closes/reopens UI on phase changes. Restore calendar/bookings/latest report without a phase change or menu side effect. Snapshot application must not settle accounts, restart a schedule or emit a new in-world event.
3. **Bounds are shift-shaped.** `SnapshotValidation.cs:34` caps day/refill day at 3; `:38` caps total guests at 6; `:99` caps reports at 3; `:103` caps maintenance at 2 and one record/day. `GameSession.Lan.cs:43` also rejects days above config totalDays. `PlanningSnapshot` caps 8 offers/6 assignments with unique room ID (`SnapshotValidation.cs:108`). Replace these with explicit bounded active/future/history collections, not unlimited arrays. Current+departing+arriving guests may exceed six *records* even though occupied rooms cannot. Different future intervals may reserve the same room.
4. **Referential integrity must survive archiving.** Incidents, responses, keys and room ownership reference guest IDs; currently every reference is validated against the six current guests. Pruning old guests needs a coordinated settled/archived-record policy. Preserve active departing ownership and unresolved/direct/drop-off references. Keep immutable report receipts independent of active guest objects.
5. **New wire values require validation.** Finite absolute times, ordered one-night intervals, allowed intent transitions/types, nonnegative revision/cost/progress, sensible capacity bounds, target existence and unique IDs. Capacity upgrades cannot exist only in host settings: current `CircuitSnapshot` carries requested load/trip duration but not mutable capacity, so replica UI would otherwise display old capacity.
6. **UI commands still need the correct interaction context.** `LanSession.cs:290` currently requires the remote Service actor to be UI-blocked for a menu command. Preserve this meaning with operations tabs and actual physical phone/conversation grants; never loosen that into remote calls or item delivery by ID alone. Report day crossing must not revoke an otherwise valid physical grant, but guest departure, distance, privacy, model replacement or expiry still must.
7. Keep bounded GZip world framing and snapshot limits; measure new DTO size rather than growing `MaxSnapshotBytes` without a bound. A read-only client may calculate a pure forecast from replicated inputs, or receive bounded forecast data, but must not tick capacity, calendar, schedules or service intent itself.
