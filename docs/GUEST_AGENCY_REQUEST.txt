PROTOTYPE 0.3 — GUEST AGENCY

==================================================
0. WHY THIS PASS EXISTS
==================================================

A full three-day solo playtest revealed a fundamental problem.

The game has a reasonable amount of activity and pacing,
but guest interaction currently feels too linear and abstract.

Example current problem:

The player receives many:

NOISE DISTURBANCE

notifications.

However:

- some have no understandable physical source;
- the player cannot determine why the noise exists;
- the player often cannot affect the underlying cause;
- many complaints feel identical;
- the same problem may create repeated notifications;
- the obvious fallback becomes compensation.

This makes guests feel like:

complaint generators

instead of:

people living inside a simulated hotel.

The goal of Prototype 0.3 is NOT:

MORE NOTIFICATIONS.

The goal is:

MORE CAUSALITY,
MORE READABILITY,
MORE PLAYER AGENCY.

==================================================
1. CORE DESIGN LOOP
==================================================

Guest-related gameplay should follow:

CAUSE
→ GUEST EXPERIENCES IT
→ GUEST REACTS
→ PLAYER UNDERSTANDS WHY
→ PLAYER CHOOSES A RESPONSE
→ WORLD STATE CHANGES
→ GUEST REMEMBERS THE RESULT.

Not:

Random complaint
→ notification
→ Offer Money.

==================================================
2. ONLY THREE SITUATION FAMILIES
==================================================

Do NOT add many new complaint types.

For Prototype 0.3 focus on only:

1. NOISE
2. TEMPERATURE
3. ROOM CONDITION

Make these three GOOD.

Do not add:

hunger;
food orders;
entertainment requests;
dozens of personal requests;
concierge errands;
random fetch quests;
complex dialogue quests.

Depth before breadth.

==================================================
3. NO ABSTRACT COMPLAINTS
==================================================

This is a hard rule.

A complaint must NOT exist unless there is an identifiable underlying cause.

Example:

INVALID:

Guest 102
Noise dissatisfaction = high
→ Noise Complaint

with no source.

VALID:

Guest in Room 103
is performing LoudTVActivity

↓

LoudTVActivity creates:
NoiseOutput = 68

↓

Room adjacency causes Room 102 to receive:
Noise = 44

↓

Guest in Room 102 has:
ComfortNoiseMax = 32

↓

Noise dissatisfaction accumulates.

↓

Guest complains.

Every noise complaint must know:

AffectedGuest
AffectedRoom
SourceType
SourceEntity
SourceRoom
CurrentIntensity

If the system cannot identify a source:

DO NOT GENERATE A NOISE COMPLAINT.

==================================================
4. NOISE SOURCES
==================================================

Create a general noise-source architecture.

Prefer something conceptually like:

INoiseSource

with:

NoiseOutput
Active
SourcePosition / Room
NoiseCategory

Possible Prototype 0.3 noise sources:

- Loud TV / music.
- Guest phone call / loud conversation.
- Guest social / loud room activity.
- Shower / plumbing noise if appropriate.
- Door repeatedly slamming if already supported.
- Actual hotel machinery ONLY if it genuinely exists.

Do NOT generate fake invisible noise.

Every source should have world feedback.

Examples:

TV:
audible through door.

Phone call:
muffled speech.

Music:
clearly audible.

Plumbing:
actual pipe / water sound.

The player should often be able to locate a source WITHOUT a quest marker.

==================================================
5. ONE PROBLEM = ONE SITUATION
==================================================

The current game must stop spamming repeated complaints for the same underlying problem.

Introduce or strengthen:

SituationInstance.

Example key:

SituationType = Noise
AffectedGuest = Guest_12
SourceEntity = TV_Room103

If this situation already exists:

DO NOT create another notification.

Instead:

update severity;
update duration;
escalate the existing Situation.

Possible stages:

Discomfort
Complaint
Frustrated
Angry
DemandsAction
LeavingRisk

A single persistent problem should remain one case.

==================================================
6. SITUATION DEDUPLICATION
==================================================

Implement a deterministic SituationKey.

Example conceptual structure:

SituationKey:
- SituationType
- AffectedGuestId
- SourceEntityId

or equivalent.

SituationSystem should:

Find existing situation.

If found:
update it.

If not found:
create it.

Do NOT let one loud TV generate 8 separate noise complaints for the same guest.

==================================================
7. ACTIVITIES ARE NOT SITUATIONS
==================================================

This distinction is critical.

ACTIVITY:

Guest watches TV.

This is normal life.

No notification.

ACTIVITY:

Guest takes shower.

Normal life.

No notification.

ACTIVITY:

Guest talks on phone.

Normal life.

No notification.

Only when activity causes meaningful negative consequences:

SITUATION.

Example:

TV itself is not a problem.

TV heard by noise-sensitive neighbor for long enough:

problem.

This will make the hotel feel busy
without turning every event into work.

==================================================
8. EXPAND GUEST LIFE — BUT KEEP IT SMALL
==================================================

Guests currently repeat too few activities.

Add enough variation for guests to feel like hotel residents.

Target approximately:

7–9 high-level activity types.

Suggested:

Arrive / CheckIn

Unpack

Rest

WatchTV

PhoneCall / Work

Shower

Sleep

LeaveHotel

ReturnToHotel

Pack / Checkout

Not every guest needs every activity.

Do NOT create a life simulator.

Activities may remain mechanically simple.

==================================================
9. GUESTS SHOULD SPEND TIME DOING NOTHING IMPORTANT
==================================================

It is completely acceptable for a guest to:

rest quietly;
sit;
sleep;
leave the hotel;
work quietly.

Not every guest should constantly create gameplay.

The hotel should have:

BACKGROUND LIFE

and

ACTIONABLE PROBLEMS.

These are different.

The player should sometimes walk through the hotel
and simply hear that people are living there.

==================================================
10. ACTIVITIES SHOULD DEPEND ON PERSONALITY
==================================================

Guest archetypes / traits should influence behavior,
not only numerical dissatisfaction multipliers.

Examples:

BUSINESS GUEST

More likely:
- Work
- PhoneCall
- early sleep

Less tolerant:
- night noise
- unresolved service problems

TOURIST / BUDGET TRAVELER

More likely:
- LeaveHotel
- ReturnLate
- WatchTV

Potentially:
- more tolerant overall

NOISY GUEST TRAIT

More likely:
- LoudTV
- LoudPhoneCall
- LoudActivity

COLD-SENSITIVE GUEST

Potentially:
- prefers warmer room;
- may take longer hot shower;
- contributes somewhat more heating demand.

Keep these differences readable during booking / planning.

==================================================
11. SCHEDULE VARIATION
==================================================

Avoid every guest doing:

Shower
→ TV
→ Sleep

Use:

Example:

Guest B:

→ work

Schedules should be reproducible enough for debugging.

==================================================
12. NOISE: PLAYER RESPONSES
==================================================

Noise must have multiple possible responses.

Example:

Room 102 complains about Room 103.

Possible player choices:

A. ASK SOURCE GUEST TO QUIET DOWN

Knock on Room 103.

Contextual action:

"Ask to keep it down."

This changes actual simulation.

Example:

NoiseOutput:
70 → 20.

Do not just mark complaint complete.

------------------------------

B. MOVE AFFECTED GUEST

Move Guest 102 elsewhere.

Requires:
- available suitable room;
- corresponding room key;
- physical relocation flow.

The noise exposure then naturally stops.

------------------------------

C. MOVE NOISY GUEST

Also valid when a room exists.

------------------------------

D. COMPENSATE

Compensation improves guest reaction / patience.

BUT DOES NOT REMOVE NOISE.

If source remains loud:

dissatisfaction can begin accumulating again.

------------------------------

E. IGNORE

Accept:
- lower satisfaction;
- worse review;
- possible escalation.

This is a legitimate management decision.

==================================================
13. ASK TO KEEP IT DOWN IS NOT MAGIC
==================================================

Do not make:

AskToKeepItDown
→ source permanently silent forever.

Guest traits should matter.

Example:

Normal guest:
usually remains quieter.

Noisy guest:
may resume loud behavior later.

Repeated requests should affect guest response.

More on memory below.

==================================================
14. TEMPERATURE SITUATIONS
==================================================

Temperature should follow the same philosophy.

Cause examples:

- boiler underperforming;
- excessive heating demand;
- room receives poor heating;
- power loss disables portable heater.

Guest experiences cold.

Possible responses:

- repair / improve boiler;
- use heater;
- move guest;
- compensation;
- ignore.

Again:

complaint must resolve because actual guest temperature experience improved
or because guest moved / left.

Do NOT resolve it by pressing:
"Resolve Temperature Complaint."

==================================================
15. ROOM CONDITION SITUATIONS
==================================================

Room-condition complaints must also have concrete causes.

Do NOT use:

RoomCondition = 42%
→ generic complaint

unless the player can understand what 42% physically means.

Use concrete state where possible.

Prototype examples:

- room not properly prepared;
- dirty linen remains;
- trash remains;
- obvious fixture is broken IF that fixture actually exists;
- room is still marked degraded because of a real supported issue.

Guest should complain about the concrete issue.

Example:

"The bed hasn't been changed."

Not:

"The room condition is poor."

If a physical/systemic cause is not implemented,
do not generate that complaint yet.

==================================================
16. SITUATION DISCOVERY
==================================================

Do not always reveal perfect information immediately.

But give enough clues that investigation is possible.

Example:

Complaint:

ROOM 102
"I can hear someone next door."

Player now knows:

source is probably adjacent.

No quest arrow required.

Walk toward Room 103.

Hear TV.

Now the cause is clear.

For temperature:

"It is freezing in here."

Player can:
- inspect room temperature;
- check boiler;
- think about moving guest.

For room condition:

"The sheets don't look clean."

Cause is obvious.

==================================================
45. ACCEPTANCE CRITERIA
==================================================

Prototype 0.3 Guest Agency is complete when:

1. No noise complaint can exist without an identifiable cause.

2. The player can discover common noise sources through the world.

3. One persistent cause does not generate repeated duplicate complaint notifications.

4. One Situation escalates instead.

5. Player can actually reduce guest-generated noise.

6. Reducing noise changes the simulation,
not just the UI.

7. Compensation does not remove the underlying cause.

8. Room relocation genuinely changes exposure.

9. Guests have lightweight memory.

10. Repeated problems can lead to different reactions.

11. Guests perform more than the original small repeating activity loop.

12. Different guest archetypes have noticeably different activity tendencies.

13. Guests can leave and return to the hotel.

14. Guests do not react to room conditions while physically away.

15. Most guest activities do NOT create notifications.

16. Notifications represent meaningful situations.

17. Temperature complaint has multiple real solutions.

18. Room-condition complaint refers to a concrete supported condition.

19. Player never receives generic unexplained "room condition bad" complaints.

20. Existing Solo mode works.

21. Existing LAN co-op continues working.

22. Existing keys / linen / boiler / electricity systems remain functional.

23. No new large hotel subsystem was introduced.

24. A complete three-day playthrough remains possible.

46. MOST IMPORTANT PLAYTEST QUESTION
==================================================

After this milestone:

When a guest complains,

does the player think:

"Okay, WHY is this happening and what do I want to do about it?"

"Another notification. Where is the compensation button?"

==================================================
47. DESIGN NORTH STAR
==================================================

Guests are not quest dispensers.

They are simulated hotel customers
whose behavior creates consequences.

A good guest situation should feel like:

"I put these people in these rooms,
they behaved this way,
the building reacted,
and now I need to decide what response is worth my time and money."

Protect that idea throughout implementation.
