## 1. Physical room keys

Six numbered physical keys come from a rack beside reception. Each uses the existing damped rigidbody grab. F / RB takes or releases an item; one E / A press while aiming at the correct waiting guest gives their assigned key. A wrong key, unprepared room, stale session or unavailable player leaves the key and reservation unchanged. Other staff cannot take an owned key.

Each room has one authoritative key with OnRack, HeldByPlayer, HeldByGuest, Dropped and Returned states. The same visible object follows its guest after handoff. Checkout returns guest-owned keys to their fixed rack docks immediately; this simple prototype policy avoids a separate key-return chore and old-roster callback loss. Dropped keys remain retrievable. A fall outside the building returns the same released key to its rack. NewGame replaces all ownership and restores the original six keys.

Relocation first reserves a clean available destination. The guest continues using the old room until a staff member brings the new key and exchanges it. At handoff, the old room becomes dirty, the old key returns and the real two-door move begins. The proposal can be cancelled; checkout also releases its pending reservation. Price and recorded experience remain attached to the stay.

Held-item interaction is an explicit capability of appropriate recipients and doors. Carrying a key does not enable unrelated repair actions. Focus ignores only the player's own held body, retaining the first other solid surface and normal reach checks. Handoff disposes the physical joint before the key presentation changes body mode. New gameplay item ownership uses logical player IDs, without camera-side tests.

The old check-in hold setting is migrated to `keyRetrievalEstimateSeconds`, used only by automated pacing adapters. It is not an interaction duration. The normal key handoff has no progress bar. The lifecycle driver explicitly labels its model key pickup/giving adapter; actual rack pickup and giving are separately covered by input/physics integration tests.

## 2. Player linen turnover

The utility room contains six real clean bundles on a shelf and a dirty-linen hamper. Every used-room checkout creates a dirty bundle on that room's bed. The guest must physically clear the room before staff can remove it. Carry that bundle to the hamper, take a clean bundle from the adjacent shelf, carry it back and hold the bed interaction for 1.5 real seconds. A ready room requires both delivery and a consumed clean bundle; no elapsed hotel time or hidden worker can complete this work.

Items use stable physical slots (`clean:0` through `clean:5`, and one `dirty:<room>` per room), with generations for later reuse. The configuration permits one to six slots so model stock cannot exceed its authored physical sources. Day-one stock is created with the session. Each successful between-day maintenance decision, including Defer, replenishes consumed slots once before the next Planning phase; StartShift and final Results do not refill. Carried and dropped stock is preserved. NewGame resets all item ownership. The bed action is exclusive per room, can run concurrently in different rooms, and loses progress when the player releases or leaves it. Cancelling keeps the clean bundle available. No optional trash task is included.

The initial housekeeper is removed from generated gameplay. Its presentation/builder can support later progression, but the current model rejects worker cleaning. The preparation ledger describes physical room needs and stock. Planning WAIT can advance actual guest departures; it cannot perform room work. The three-day diagnostic tour uses explicitly labelled model linen commands; physical interaction is verified separately with actual input and rigidbody carrying.

The physical route exposed a real door-swing trap: opening from inside pushed the held bundle behind the leaf. Guest-room doors now select an opening arc away from the interacting player when fully closed, and retain that arc when a partial closing is interrupted. Their rigidbody/collider interaction remains solid. Electrical and boiler panel covers keep their original opening behavior.

## 3. Noise counterplay

A contextual interaction at the occupied room door lets staff knock and request quiet without entering the guest's room. The command validates the present staff actor and a currently powered, loud in-room activity. A guest with the Noisy trait agrees for up to 25 hotel seconds; the normal Budget profile has this trait. Other guests agree until their scheduled checkout. Repeating a request during the current agreement does not extend it. The real music/television source falls to 15% while the agreement lasts, so neighboring rooms recover through the existing measured noise and need rules. Shower noise remains unchanged. Activity schedules, electrical demand and room adjacency are not overwritten to simulate a successful response.

Moving either the affected guest or the noisy guest uses the existing destination reservation and physical key exchange. Source/receiver locations change only through that room-transfer lifecycle. A guest settles into QuietRest after reaching the new room; acoustic comparison tests explicitly resume a loud activity after arrival to distinguish distance from this settling behavior. Operational situations are not resolved merely because a complaining guest is walking between rooms, and price, identity and recorded experience remain attached to the stay.

The first accepted compensation credit lowers current dissatisfaction for the guest's active reasons by 0.35, clamped to zero, and closes those operational cases for a 25-second response pause. It changes neither sound/heat sources nor severity, lifetime exposure, quality history or agreed price. Repeated credit requests still fail and cannot extend the pause. During a physical transfer the relief timer freezes. If the unchanged cause remains after the pause, a fresh Observed episode begins and must meet the ordinary exposure/dissatisfaction thresholds before complaining again. Real recovery still requires the existing 8-second hysteresis and applies the 12-second reopening cooldown. Checkout clears remaining relief. The separate Accept consequences action continues to acknowledge current attention while leaving the cause and its costs active.

## 4. Minimal LAN foundation

Netcode for GameObjects 2.7.0 with Unity Transport 2.7.4 supplies host/join-by-IPv4 transport. Each computer owns one full-screen camera and local input. The host owns hotel time, economy, guest routes, room/infrastructure state and important physical bodies. The client sends input/ledger intentions and receives explicit model/world snapshots; its model cannot advance, pay, clean or repair independently. The old local split-screen setup remains a development option.

The host maps the approved peer to logical actor1. Inputs have a 0.35-second lease, bounded finite vectors and monotonic epoch/sequence; stale or disconnected actors release their holds and joints. Short input edges are merged between host frames, while bed work and repair use host elapsed time. Menu pause sends neutral inputs; loss of local focus releases only that computer's actions. Client status indicates when the host paused.

Typed snapshots include all three day reports, planning and finite item ownership. Validation precedes application; invalid or stale state cannot partially replace the live client model. Optional IDs are canonicalized after Unity JSON represents null strings as empty strings, including unused heaters and dirty beds without a clean set. No client physics prediction, Steam service, relay or host migration was added.
